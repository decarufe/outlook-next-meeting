# Spike #2 — Disponibilité des widgets tiers + versions Windows App SDK

## Question

Résoudre les points `[à vérifier]` de `docs\architecture.md` sur la disponibilité réelle des widgets tiers Windows 11, les versions Windows App SDK à cibler, et les contraintes de distribution/packaging.

## Findings

- **Les widgets tiers ne sont plus seulement un sujet Insider dans la documentation courante.** La documentation Microsoft Learn décrit le Widgets Board Windows 11 comme l’hôte courant, indique que les widgets peuvent être fournis par une application Win32 packagée ou une PWA, et documente le flux de publication après développement/test. Sources : Windows Widgets (`https://learn.microsoft.com/en-us/windows/apps/design/widgets/`), Widget providers (`https://learn.microsoft.com/en-us/windows/apps/develop/widgets/widget-providers`), tutoriel C# (`https://learn.microsoft.com/en-us/windows/apps/develop/widgets/implement-widget-provider-cs`).
- **Historique important : Windows App SDK 1.2 a introduit les widgets tiers, mais en pratique c’était encore du test local via Windows Insider.** Les notes 1.2 disent que les développeurs tiers pouvaient créer des widgets pour des apps Win32 packagées et les tester localement; les prérequis explicites de cette release étaient Developer Mode + Windows Insider Dev Channel build `>= 25217` + Widgets Board `521.20060.1205.0+`. Source : `https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-1-2`; blog Windows App SDK 1.2 : `https://blogs.windows.com/windowsdeveloper/2022/11/16/whats-new-in-windows-app-sdk-1-2/`.
- **API de base : `IWidgetProvider` existe depuis Windows App SDK 1.2.** La référence API liste les monikers `windows-app-sdk-1.2` et plus récents pour `Microsoft.Windows.Widgets.Providers.IWidgetProvider`. Source : `https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.widgets.providers.iwidgetprovider`.
- **Fonctionnalité de personnalisation : `IWidgetProvider2` arrive avec Windows App SDK 1.4.** La référence API de `IWidgetProvider2` commence à `windows-app-sdk-1.4`; les release notes 1.4 ajoutent `IWidgetProvider2`, `IWidgetProviderAnalytics`, `IWidgetProviderErrors` et l’attribut manifeste `IsCustomizable`. Sources : `https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.windows.widgets.providers.iwidgetprovider2`, `https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-notes/windows-app-sdk-1-4`.
- **Version SDK recommandée aujourd’hui : utiliser la dernière version stable supportée, pas 1.2.** Au 2026-09-22, Microsoft Learn liste Windows App SDK **2.5.1** comme dernière version stable et production-ready. Le tutoriel widget C# actuel demande `Microsoft.WindowsAppSDK` **2.3.1 ou plus récent**. Sources : release channels (`https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/release-channels`), downloads (`https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/downloads`), tutoriel C# (`https://learn.microsoft.com/en-us/windows/apps/develop/widgets/implement-widget-provider-cs`).
- **Version Windows 11 requise : Microsoft Learn courant confirme “Windows 11 Widgets Board”, mais ne donne pas une ligne nette “22H2 vs 23H2 vs 24H2” pour la production.** La seule exigence chiffrée trouvée dans Learn est l’exigence historique Insider `build >= 25217` de Windows App SDK 1.2. Les docs courantes parlent de Windows 11 sans réintroduire cette exigence Insider. Donc : on peut prendre une décision produit, mais il faut rester honnête que le minimum exact 22H2/23H2/24H2 n’est pas explicitement confirmé par Learn.
- **Distribution/packaging : les providers Win32 doivent être packagés.** Learn dit que, pour les apps Win32, “only packaged apps are currently supported” et que l’enregistrement se fait dans `Package.appxmanifest`. Le tutoriel C# fait créer un projet MSIX, déployer localement pour tester, puis indique de publier l’app dans le Microsoft Store pour que les utilisateurs installent les widgets. Sources : manifeste widget (`https://learn.microsoft.com/en-us/windows/apps/develop/widgets/widget-provider-manifest`), tutoriel C# (`https://learn.microsoft.com/en-us/windows/apps/develop/widgets/implement-widget-provider-cs`).
- **Sideload/dev : oui pour développement.** Le tutoriel C# demande Developer Mode, build/deploy du package local et vérification dans le Widgets Board. Source : `https://learn.microsoft.com/en-us/windows/apps/develop/widgets/implement-widget-provider-cs`.
- **PWA : possible, mais hors choix MVP.** Learn documente aussi les widgets PWA et précise une livraison via Microsoft Store/PWABuilder pour les utilisateurs. Source : `https://learn.microsoft.com/en-us/microsoft-edge/progressive-web-apps/how-to/widgets`.

## Décision/Recommandation

1. **Cibler une app Win32/C# packagée MSIX avec Windows App SDK stable courant.** Pour le scaffolding MVP, utiliser `Microsoft.WindowsAppSDK` **2.5.1** si disponible dans NuGet au moment de l’implémentation, sinon la dernière stable 2.x supportée. Ne pas baser le projet sur 1.2 : l’API existe, mais la version est hors support et son contexte widgets était Insider/local-test.
2. **Minimum produit Windows : Windows 11 supporté, recommandé 23H2+ / 24H2.** Ne pas promettre Windows 11 22H2 comme cible de production tant que le test réel n’est pas fait; 22H2 est acceptable comme opportunité “best effort” seulement si le Widgets Board courant y expose le provider. Les validations MVP doivent au minimum couvrir **23H2 et/ou 24H2**.
3. **Distribution MVP : MSIX sideload/dev d’abord; Store pour distribution utilisateur.** Les issues d’implémentation doivent supposer un package MSIX signé/déployable localement. La publication Store reste la voie documentée pour les utilisateurs finaux, à planifier après validation technique.
4. **Ne pas utiliser PWA pour v1.** Le choix C#/.NET + Win32 packaged app reste aligné avec l’architecture et donne accès au modèle `IWidgetProvider`.

## Impact sur les issues dépendantes

- **#5 scaffolding** : créer dès le départ une app packagée MSIX/Windows Application Packaging Project, avec `Microsoft.WindowsAppSDK` stable 2.x. Prévoir `net8.0-windows10.0.19041.0` côté projet C# comme dans le tutoriel, mais documenter que la cible produit est Windows 11.
- **#6 provider** : implémenter `IWidgetProvider` uniquement pour le MVP. Ne pas implémenter `IWidgetProvider2` sauf si Naomi/Holden décident d’ajouter la personnalisation; si nécessaire, cela impose Windows App SDK 1.4+ — déjà couvert par 2.x.
- **#11 packaging** : packaging MSIX non optionnel. Prévoir signature dev/sideload, identité stable, manifeste `windows.comServer` + `windows.appExtension`. Préparer plus tard la piste Microsoft Store si distribution hors dev.

## Incertitudes restantes

- Microsoft Learn ne confirme pas explicitement, dans une page courante, le seuil exact **22H2 / 23H2 / 24H2** pour widgets tiers en production. Décision prudente : tester sur 23H2/24H2, ne pas garantir 22H2.
- Les contraintes Store peuvent évoluer. La documentation consultée décrit le Store comme voie de publication utilisateur, mais ne tranche pas clairement si une distribution entreprise hors Store est supportée pour tous les scénarios utilisateurs.
- Le comportement dépend aussi de la version installée du Widgets Board, qui n’est pas exposée comme un simple prérequis produit dans les docs courantes.
